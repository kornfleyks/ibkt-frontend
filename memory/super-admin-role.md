Built on request (2026-10-04). Decisions (user, don't re-ask): Super Admin keeps every Admin permission plus the extra-restricted pages (treated as "Admin or higher" everywhere via shared helpers, not a separate standalone permission set); it's a real Monday status label on the Users board's Role column (created the same way "Blocked" was, via `create_labels_if_missing`); the two accounts are fully protected from every other Admin (and each other) on the Users page - role and status both locked, server-enforced.

Key files: `src/constants/roles.js` (`ROLES.SUPER_ADMIN`, `isAdminRole(role)`, `roleSatisfies(requiredRoles, role)`, `SUPER_ADMIN_EMAILS`, `isSuperAdminEmail(email)` - this is the one module both server and frontend import, no duplicate). About 25 call sites across server and frontend were switched from literal `role === "Admin"` / `hasRole('Admin')` to these helpers (server: auth.js requireAdmin, applicationAccess.js, index.js x3, jotform/secondStage/handler.js, mondayApiVersionCheck.js, postAdoption/routes.js x2, caseOwner.js canAssignCaseOwner, database/sync.js, preAdoption/routes.js CAN_ADD; frontend: ProtectedRoute.jsx, utils/navigationAccess.js, AuthContext.jsx (+`isAdmin` on useAuth), MentionLink.jsx, AdoptionDetail.jsx, MondayApiVersionBanner.jsx, Sidebar.jsx, Dashboard.jsx, utils/ownership.js, utils/recentActivity.js, constants/permissions.js). `ROLES.SUPER_ADMIN` filtered OUT of: Users.jsx role picker, settingDefinitions.js CASE_OWNER_ROLES/CASE_OWNER_ASSIGNER_ROLES option lists - never a role anyone selects, only ever set by the script.

Server enforces the "fully protected" rule, not just the frontend: `server/users.js` (`changeUser`/`toColumnValues`) refuses ANY field change to a protected account, and refuses setting any account's role TO Super Admin; `server/userAdmin.js` status endpoint refuses a status change to a protected account. Tested all three refusals without writing.

State 2026-10-04: `scripts/seedSuperAdmins.js` run - both accounts are "Super Admin" on Monday (confirmed via a direct, uncached Monday read) and in the local database mirror (one of the two, support@, mirrored a step behind at first - the `mondayDirectRequest` mutation goes through `mondayFetch`/`database/mirror.js` like any app write, but the second of two near-simultaneous writes didn't mirror; fixed with a one-off local UPDATE to match Monday's confirmed value, no further action needed). The ALREADY-RUNNING local `npm run dev:all` process still has both accounts' OLD role cached in memory (`accountState.js` loads once at server start) - needs a restart to pick up Super Admin locally; Render will read the current value on its own next deploy/restart regardless.

**Why:** the user wants two specific accounts (their own and the client's support inbox) to have full Admin power plus the extra pages, permanently, with nobody (including other future Admins) able to demote or lock them out by mistake.

2026-10-04 (same day, follow-up): App Settings, Client Review and the sidebar's API usage counters (Monday/database call counts) were moved from email-gating to role-gating - `roles: ["Super Admin"]` in `navigation.js`/`AppRoutes.jsx` (not `["Admin"]`: `roleSatisfies` only widens Super Admin INTO an Admin gate, never the other way, so a plain Admin is correctly excluded), and `isSuperAdmin` (new, alongside `isAdmin`) on `useAuth` for the sidebar counters. The `emails` prop on `ProtectedRoute`/nav items still exists for one-off cases but these three no longer use it. Also that day: the sidebar counters' `APP_ENV === "development"` guard was dropped (`src/components/Sidebar/Sidebar.jsx`) - they now show for Super Admins in every environment, including production.

**How to apply:** when adding a NEW Admin-only check, use `isAdminRole`/`roleSatisfies`, not a literal `"Admin"` string, so Super Admin keeps parity automatically. For something only Super Admin (not regular Admin) should reach, gate on `roles: ["Super Admin"]` / `isSuperAdminRole` / `isSuperAdmin`, not email lists. Related: [[review-items]].
